# 이력서 문장 ↔ 증거 대응표

2026-09-12. Codex 가 읽을 문서다.
[프레임워크](20-development-evidence-framework.md) · [청사진 채점](blueprint-status.md) 과 함께 본다.

2차 피드백 [권장] 3번이 **"선택마다 판정 근거가 된 측정을 한줄씩 붙이기"** 다.
이 문서는 **불릿마다 붙일 숫자가 지금 있는지 없는지**만 가른다.

## 0. 먼저 — 목차와 임베딩은 다른 자리다

`21-embedding-shortlist.md` 는 **임베딩(6번 자리)** 문서다. 목차(4번 자리)가 아니다.
사용자가 이 둘을 같은 것으로 알고 있었으므로 문서 제목이나 첫 줄에서 어느 자리인지 분명히 한다.

| 자리 | 지금 단계 | 문서 |
|---|---|---|
| 4 목차 생성 | ③ 측정까지 했으나 통과 기준을 사전에 안 적음 | `data/evals/2026-09-09*` |
| 6 임베딩 | ② 후보 추리기까지. 비교 미실행 | `21-embedding-shortlist.md` |

21번 문서의 마지막 문단("조사만으로 '세 모델을 비교해 선정'이라고 쓰지 않는다")이 맞다.
그대로 지킨다.

## 2. 그대로 옮길 수 있는 숫자

### 목차 — 같은 26문단, 같은 프롬프트

통과 = JSON 유효 + 제목 25자 이내 + 인용문이 원문에 그대로 있음.

| 후보 | 통과 | 흔들림 | 평균 응답 | 출력 토큰 |
|---|---:|---:|---:|---:|
| Claude Haiku 4.5 | 24/26 | 0 | 1310ms | 70 |
| qwen3.8-27b | 24/26 | 0 | 479ms | 33 |
| Claude Sonnet 5 | 25/26 | 11 | 1894ms | 78 |
| gpt-oss-20b | 22/26 | 0 | 3247ms | 664 |
| gpt-oss-120b | 19/26 | 4 | 2714ms | 590 |
| qwen3.6-27b | 0/26 | 0 | 41904ms | 800 |

운영 코퍼스 89문단 중 폴백 1개, 1회 통과 86개.

**"비교"까지만 쓴다. "선정"은 못 쓴다.** 이유 둘.
① 통과 기준을 측정 전에 안 적었다.
② Sonnet 5 는 `temperature is deprecated for this model` (400) 로 온도 없이 따로 돌렸다.
나란히 놓고 잰 게 아니다.

### 의미 검색 — 기준선

질문 10건(답 있음 8, 없음 2), 영상 8편·89문단, `top_k=3`, 임계치 없음.

| 항목 | 결과 |
|---|---:|
| 상위 3위 안 시간 구간 적중 | 8/8 |
| 본문 확인 후 완전 적중 | 7/8 |
| 부분 적중 | 1/8 |
| 무관 질문 거절 | 0/2 |

점수 분포가 겹친다 — 답 있음 1위 0.545~0.667, 답 없음 0.544 와 0.619.
**거절 0/2 를 이력서에 쓰는 편이 낫다.** 재보고 못 넘긴 것을 아는 사람으로 읽힌다.

### 전사

`mode=generate` 가 **작업 번호(HTTP 202)를 돌려주는 데만** 91.8초.
Vercel 무료 함수 상한 60초 초과. "전사에 91.8초" 가 아니라 "작업 번호 반환까지 91.8초" 다.

## 3. 숫자가 없는 곳 — 하나뿐이다

**문단 나누기.** "문장 중간 끊김을 줄이고" 를 뒷받침할 전/후 측정이 v2 에 없다.
v1 의 "끊김 0%" 는 다른 코드의 숫자라 v2 불릿에 못 쓴다.

그런데 이 자리는 **이미 해법이 둘 있어서 새로 만들 게 없다.**

| 해법 | 위치 | 방식 |
|---|---|---|
| 무음 기반 | `main` | 조각 시각 간격 ≥ `PAUSE_SEC` 0.3초를 문장 끝으로 |
| 어미 기반 | `fix/timestamp-release` | 종결어미 정규식, maxlen 초과 + 구두점 없을 때만 |

같은 전사문에 세 조건(무음만 / 어미만 / 둘 다)을 돌려
**문장 중간에서 끊긴 청크 수**를 세면 끝난다. 지표가 이미 정의돼 있어
통과 기준을 실행 전에 적기도 쉽다. 병합 충돌도 이 측정으로 함께 풀린다.

## 4. 다음 작업 순서

1. **문단 나누기 비교** — 가장 싸다. 코드 둘 다 이미 있다.
   실험 카드에 통과 기준(끊긴 청크 수 상한)을 먼저 적고 세 조건을 돌린다.
   결과가 `chunker.ts` 병합 결정과 이력서 불릿을 동시에 해결한다.
2. **목차 상위 2~3개 동일 조건 재실행** — 여섯을 다시 돌릴 필요 없다.
   전부 온도 없이 같은 조건으로 돌리면 "비교 후 채택" 으로 올라간다.
3. **임베딩 비교** — 21번 문서의 설계대로. 통과 기준과 비용·지연 상한을
   실행 전에 사용자에게 확정받는다.

## 5. 이력서에서 고쳐야 할 사실 오류

- Keyword 줄의 `Claude Haiku` → `claude-sonnet-5`
- Keyword 줄의 `FastAPI` → v2 에 없다. Next.js API Route
- "자막 수집" 이라는 라벨 — yt-dlp 로 받은 건 자막이 아니라 **음성**이고
  받아쓰기는 mlx-whisper 가 했다. native 자막 전환과 구분이 안 된다

Codex 가 같은 89문단·같은 10문항으로 두 모델을 돌렸다.
**사전 조건을 실행 전에 정했다** — "답 있는 질문의 hit@3 유지".

| 모델 | hit@3 | 정답 1위 | MRR |
|---|---:|---:|---:|
| nlpai-lab/KURE-v1 | 8/8 | 4/8 | 0.729 |
| BAAI/bge-m3 | 7/8 | 3/8 | 0.594 |

BGE-M3 가 조건을 못 넘겨 **KURE-v1 유지**. Q03 이 2위에서 4위로, Q06 이 1위에서
3위로 밀린 것이 hit@3 하락의 원인이다. 운영 DB·배포 모델은 안 바꿨다.

산출물: `web/data/evals/search/runs/2026-09-11T08-10-06-812Z-dev/embedding-comparison-2026-09-12/`

## 이력서에 미치는 영향

2차 피드백이 예시로 준 문장이 **이제 참이 된다.** 다만 "선정"이 아니라 "유지"다.

> 구어체 전사문 검색이라는 조건으로 후보를 추리고, 영상 8편·89문단에서 만든
> 검수 질문 10건으로 KURE-v1 과 BGE-M3 의 상위 3위 적중률을 비교(8/8 대 7/8,
> MRR 0.729 대 0.594)해 KURE-v1 유지를 결정.

남은 한계 둘. 기존 10문항을 재사용한 개발 비교라 **새 질문으로 하는 최종 확인**이
남았고, 비교한 후보는 2종이다(Qwen 은 조건부 후보로 미실행).

# 부록 B. 병합하면서 발견한 지표 결함

무음 분할을 `pauseSec` 선택지로 되살리고 합성 자막으로 확인했다.

```
끔 (기본):    {"n":1,"avg":140,"cut":1,"cut_pct":100}
켬 (0.3초):   {"n":3,"avg":46,"cut":3,"cut_pct":100}
```

침묵 자리에서 정확히 갈렸고 각 청크가 "…중요한데요" "…생각합니다" "…왔거든요" 로
끝난다. 눈으로 보면 확실히 나아졌다. **그런데 `cut_pct` 는 양쪽 다 100% 다.**

`stats()` 의 `cut` 은 `ENDS` 정규식(`[.!?。？！]` 로 끝나는지)으로 센다.
구두점이 없는 전사에서는 **어떻게 잘라도 100% 가 나온다.** 문단 나누기 비교의
지표로 그대로 쓸 수 없다.

대안 셋 중에 골라야 한다.

1. 종결어미로 끝나는지 세기 — 어미 기반 분할에 유리하게 기울 수 있다
2. 사람이 청크 끝을 보고 문장이 끝났는지 판정 — 표본이 작으면 가능
3. 구두점이 있는 전사문으로만 비교 — 정작 고치려는 경우를 못 잰다

이 선택이 통과 기준의 일부다. **비교 실행 전에 정한다.**

# 부록 C. 지금 제출 가능한 Digestube 항목 — 확정 문안 (2026-09-12)

배포된 v2 가 실제로 하는 것만 적었다. 아래 "앱 작업 → 풀리는 문장" 이 끝날 때마다 해당 줄을 갱신한다.

### Digestube — 유튜브 영상을 문단·목차로 읽고 뜻으로 검색하는 웹 서비스
개인 · 2026.08 – 진행 중 · digestube.vercel.app · github.com/7inug1/digestube

유튜브 주소를 받아 외부 전사 API로 전사하고, 문단으로 나눠 임베딩한 뒤, 질문과 뜻이 가까운 문단을 찾아 보여주는 RAG 검색 서비스

- **음성 수집·전사**: 로컬의 yt-dlp 음성 수집·mlx-whisper 받아쓰기 방식이 배포 서버의 유튜브 접근 차단으로 동작하지 않아 Supadata로 전환.
- **배포 제약 대응**: Supadata의 받아쓰기 요청이 작업 번호를 반환하는 데만 91.8초가 걸려 서버의 요청 처리 제한인 60초를 초과. 영상에 이미 등록된 자막을 Supadata로 가져오는 방식(native)으로 전환하고 정상 동작을 확인.
- **청킹**: 문장이 중간에서 끊기지 않고 검색에 필요한 문맥이 유지되도록, 문장 경계를 기준으로 여러 문장을 일정 분량으로 묶도록 구현.
- **목차**: 전사문을 빠르게 훑을 수 있도록 LLM으로 문단별 제목을 생성하고, 함께 반환한 근거 문장이 원문에 있는지 대조. 후보 6종을 같은 26문단에 돌려 근거 대조 통과율·응답시간을 비교(상위 3종 24~25/26, 0.5~1.9초)했고 현재 Claude Sonnet 5 사용. 검증 실패 시 재시도하고, 최종 실패 시 원문 첫 문장을 축약해 목차가 비지 않도록 처리.
- **저장소**: PostgreSQL의 pgvector로 유사한 문단을 찾으면서 본문·타임스탬프도 함께 조회하도록 구성. 별도 벡터 DB 없이 데이터를 관리하고, 서버와 DB 사이의 통신 거리를 줄이기 위해 Vercel과 Supabase를 모두 서울 리전에 배치.
- **임베딩**: 한국어 구어체 질문에서 실제 답을 담은 문단을 우선 검색하는 것을 기준으로 KURE-v1과 BGE-M3를 비교. 영상 8편·89문단에서 만든 검수 질문 10건 중 답 있는 8건의 상위 3개 적중률이 KURE-v1 8/8, BGE-M3 7/8로 KURE-v1을 유지.
- **의미 검색**: 질문과 전사문에 같은 단어가 없어도 관련 내용을 찾도록 질문과 문단을 벡터로 변환해 유사도 상위 3개를 본문·타임스탬프와 함께 표시. 같은 10건 기준선에서 답 없는 질문 2건을 거절하지 못한 것을 확인하고 거절 장치를 다음 과제로 남김.

Keyword · Supadata, KURE-v1 (BGE-M3 비교), pgvector, Supabase, Claude Sonnet 5, Next.js, TypeScript, Vercel

## 앱 작업 → 풀리는 문장

| 순서 | 앱 작업 | 끝나면 바뀌는 줄 |
|---|---|---|
| 1 | 구두점 없는 한국어 영상 3~5편 추가 → 청킹 3방식(어미/무음/둘 다) 블라인드 검수. 점수 기준은 화면 만들기 전에 카드에 적는다 | 청킹: "…N편·N문단에서 세 방식을 검수해 문장 완결성 N/N·문맥 N/N으로 X 방식을 선정" |
| 2 | 목차 상위 2~3종을 **전부 온도 없이** 같은 조건으로 재실행. 통과 기준 사전 기록 | 목차: "비교했고 현재 사용" → "비교해 선정" |
| 3 | 새 질문으로 KURE-v1 최종 확인 | 임베딩: "유지" 를 새 질문 결과로 뒷받침 |
| 4 | 답변 생성 + 거절 임계치 구현 | 헤더: "찾아 보여주는" → "찾아 답하는" · 의미 검색의 "다음 과제로 남김" 삭제 · **물어보기** 불릿 부활 |
