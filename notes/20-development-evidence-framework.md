# Digestube v2 개발·평가·이력서 공통 기준

2026-09-12. 사용자가 인용한 `신진욱_2차.md` 피드백을 작업 기준으로 채택한다.
기존 방법론의 후보 전수 나열보다 아래의 실패 정의 → 소수 후보 → 자체 검증 순서를 우선한다.

## 1. 기본 순서

1. **실패를 정의한다.** 사용자가 어떤 불편을 겪는지 구체적인 사례로 쓴다.
2. **통과 기준을 적는다.** 품질 지표·허용 실패 수·비용·지연 한도·채점 방법을 비교 실행 전에 고정한다. 숫자는 제품 요구에서 정하며 외부의 보편적인 합격선처럼 쓰지 않는다.
3. **후보 2~3개를 추린다.** 현재 방식을 기준선으로 포함하고 후보를 넣거나 뺀 이유를 기록한다. 외부 벤치마크는 후보를 추리는 자료이며 자체 성능 증거가 아니다.
4. **같은 자체 데이터로 비교한다.** 질문·정답·조건을 고정하고 한 번에 한 조건을 바꾼다. AI가 초안을 만들고 사용자가 마지막에 검수할 수 있으며 작성자와 판정자를 구분한다.
5. **선택하고 마무리한다.** 필수 품질·운영 조건을 충족한 후보 중 사전에 정한 비용·지연·복잡도 기준으로 결정한다. 튜닝에 쓰지 않은 새 사례로 확인한 뒤 종료한다. 모두 미달하면 실패 원인을 기록하고 다음 실험 하나를 정한다.
6. **근거를 이력서로 옮긴다.** 문제 → 후보/판단 → 측정 결과 → 적용한 결정 순으로 쓴다. 앱 배포와 문서의 상태를 일치시킨다.

현재 v2 범위는 native 자막 등록 → 문단 → 목차 → 읽기·의미 검색이다. 요약·핵심 하이라이트·답변 생성은 이 프레임워크 채택만으로 범위에 추가하지 않는다.

## 2. 실험 하나당 기록할 카드

```text
주제 / 날짜 / 담당:
사용자에게 보이는 실패와 실제 사례:
상태: 미검증 / 기준선 측정 / 비교 중 / 검증 후 채택 / 제약으로 채택
필수 품질 기준(지표, 분모, 허용 실패 수):
비용·응답 시간 한도와 측정 방법:
동률이면 선택할 기준 / 종료 조건:
후보 2~3개와 선정·제외 이유:
고정 데이터 버전 / 정답 / 채점 기준 / 사람 검수 상태:
고정 조건 / 이번에 바꾸는 조건:
실행 코드·명령 / 커밋 / 모델 ID·설정 / 프롬프트:
응답 원문 / 실행 오류 / 반복 횟수 / 비용·지연 / 결과 파일:
관측 결과 / 사후 해석 / 결정 / 미해결 한계:
새 사례로 최종 확인한 결과:
배포 상태와 확인 기록:
현재 증거로 쓸 수 있는 이력서 문장:
```

모델에 따라 지원하지 않는 설정은 차이를 명시한다. 형식 실패·429·타임아웃도 운영 실패로 남기되 의미 품질 실패와 구분한다. 성공한 실행만 골라 합치지 않는다.

## 3. 현재 상태에 적용

| 대상 | 사용자에게 보이는 실패 | 평가할 것 | 현재 증거와 다음 단계 |
|---|---|---|---|
| 자막 수집 | 자막을 못 가져오거나 다른 언어가 옴 | 등록 성공, 언어, 시간 초과, 실패 안내 | native는 배포 제약에 따른 선택. 정확도 비교 우승으로 쓰지 않는다. 기존 운영 검증을 활용한다. |
| 청킹·검색 문맥 | 문장/설명이 갈라져 검색 결과만으로 내용을 이해하지 못함 | 문장 끊김, 정답 근거의 완결성, 읽는 분량 | Q03 부분 적중 사례 존재. 현재 방식과 이웃 문단 제공 등의 후보를 비교하기 전에 기준을 적는다. 청킹 비교는 동일 글자 예산도 사용한다. |
| 검색·임베딩 | 원하는 대목을 못 찾음 | 상위 3개 적중과 본문의 실제 근거를 별도 평가 | KURE-v1 기준선만 측정. 타 모델보다 우수하다고 결론 내리지 않는다. 먼저 실패가 문단 경계·순위·모델 중 어디서 생기는지 구분한다. |
| 무관 결과 처리 | 질문에 답이 없는데 관련 있어 보이는 결과가 나옴 | 답 없음의 올바른 거절과 답 있음의 손실, 추가 비용·지연 | 2문항 모두 거절 실패. 단순 임계치 사후 분석은 개선 근거 부족. 관련성 재판정 등을 후보로 검토하되 아직 채택하지 않았다. |
| 목차 | 제목이 문단을 대표하지 못하거나 주장을 덧붙임 | 핵심 대표성, 원문 충실성, 목차만으로 이해 가능성; 형식·인용 일치·비용은 별도 | Sonnet 5 잠정. 사람 품질 평가는 보류 상태. 재개 시 동일 문단으로 2~3개 후보를 비교한다. |

인용 문장이 원문에 있다는 자동 검사는 제목이 올바른 요약임을 보장하지 않는다. 목차 품질을 인용 일치율만으로 판정하지 않는다.

## 4. 이미 측정한 검색 결과의 취급

- 사용자 검수 10문항(답 있음 8, 답 없음 2), 영상 8편·89문단에서 기준선 측정 완료.
- 시간 겹침 자동 적중 8/8, 올바른 거절 0/2, 실행 오류 0건.
- AI 본문 검토는 명확한 적중 7/8·부분 적중 1/8. 검색 결과 의미 품질에 대한 사용자 최종 판정은 아니다.
- 합격선 없이 진행한 **기준선 측정**이다. 지금 정한 기준을 과거에 미리 정했던 것처럼 쓰지 않는다.
- 같은 10문항은 개발 비교에 쓴다. 이미 결과를 봤으므로 최종 독립 확인용으로 재분류하지 않는다.
- 이후 비교의 합격선은 아직 미확정이다. 다음 실험 카드에 제안하고 실행 전에 확정한다.
- 원본과 해석: [검색 기준선](../web/data/evals/search/runs/2026-09-11T08-10-06-812Z-dev/analysis.md), [평가 절차](18-search-evaluation.md).

## 5. 이력서 작성 규칙

비교 후 채택한 경우:

> [실패/요구]를 기준으로 [후보 N개]를 추리고, [자체 데이터 N건]에서 [지표와 결과]를 비교해 [방식]을 적용.

기준선만 측정한 현재 검색의 예:

> 사용자 검수 질문 10개로 검색 평가를 구성하고, 상위 3개 결과의 정답 구간 포함 여부와 무관 질문 거절 여부를 측정해 문맥 누락·무관 결과 반환 사례를 확인.

제약 때문에 선택한 경우:

> [실측한 운영 제약]으로 [기존 방식]을 사용할 수 없어 [대안]을 적용하고, [실제로 확인한 동작]을 검증.

`구현`, `측정`, `비교 후 채택`, `배포`를 구분한다. 미측정 수치·미구현 기능은 넣지 않는다. 표본 수, AI/사람 판정 여부, 개발용/최종 확인용 구분은 상세 기록에 보존한다. 모든 기술에 억지로 모델 비교를 만들지 않는다.

## 6. 다음 작업 순서

1. 검색 실패 두 유형(문맥 누락 / 무관 결과)을 위한 실험 카드를 각각 작성한다. 기존 결과를 활용하고 처음부터 다시 만들지 않는다.
2. 한 카드의 통과 기준과 후보를 먼저 확정하고, 한 가지 변경을 비교·검수한다.
3. 새 사례로 확인한 후 제품에 반영하고 배포 상태를 기록한다.
4. 그 증거로 Digestube 이력서 문장을 갱신한다. 목차 평가는 보류를 해제할 때 같은 틀로 진행한다.

AI가 후보 조사·카드 초안·구현·실행·결과 정리를 맡는다. 사용자는 제안된 제품 기준과 최종 사례의 적합성을 검수한다. 새로운 수치 목표나 품질 판정을 사용자 승인으로 임의 기록하지 않는다.
