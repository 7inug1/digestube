# 검색 평가 기록

## 지금 하는 일

현재 검색이 원하는 영상 대목을 찾는지 확인한다. 먼저 질문과 정답 구간을 사람이 검토하고, 그다음 검색한다. 목차 평가와 답변 생성 평가는 이번 범위에 포함하지 않는다.

상태: **AI 초안 10문항으로 축소 · 사용자 검토 전 · 검색 실행 전**.

## 기준 — 첫 평가에 사용할 초안

| 항목 | 방법 |
|---|---|
| 검색 범위 | 등록된 전체 영상. 정답 영상으로 검색 범위를 미리 제한하지 않는다. |
| 답 있는 질문 | 상위 3개 결과 중 정답 영상의 정답 시간 구간과 겹치는 결과가 있으면 적중. |
| 답 없는 질문 | 전체 코퍼스에 답이 없음을 검토한 질문에서 결과가 비어 있으면 올바른 거절. |
| 놓친 질문 | 답이 있는데 결과가 비어 있는 경우를 별도로 센다. |
| 의미 확인 | 시간만 겹치고 실제 답의 근거가 없는 경우 별도 표시한다. 겹침만으로 검색 품질 전체를 설명하지 않는다. |
| 합격선 | 미확정. 이전 대화의 80%는 예시이며 수업 기준이나 검증된 목표가 아니다. 첫 실행은 현 상태 측정으로 기록한다. |

시간 겹침은 `검색 시작 < 정답 끝` 그리고 `검색 끝 > 정답 시작`으로 판정한다. 반드시 영상 ID도 같아야 한다. 정답은 문단 번호가 아닌 영상과 시간 구간으로 남긴다. 복수의 정답 구간이 있으면 모두 기록한다.

상위 3개 방식은 현재 검색의 기준선 측정용이다. 나중에 청킹을 비교할 때는 문단 크기에 따른 유리함을 줄이도록 같은 글자 예산에서의 성능도 별도로 설계한다. 결과를 본 뒤 현재 채점 규칙을 몰래 바꾸지 않는다.

## 준비 순서

1. 질문을 작성한다. 문단 제목이나 검색 결과를 보고 정답 표현을 그대로 베끼지 않는다. AI 초안은 작성자를 표시한다.
2. 사용자가 질문이 자연스러운지, 정답 구간에 실제 근거가 있는지 확인한다. 답 없는 질문은 전체 영상 기준으로 확인한다.
3. 검토가 끝난 질문·정답·채점 기준을 버전으로 고정한다. 최종 문항 수와 언어·영상별 분포를 기록한다.
4. 영상 revision·본문 해시·벡터 해시, 평가 코드/앱 커밋, 모델, 검색 범위, top_k, 임계치 적용 여부를 저장한다. 현재 작업 기록의 8편·89문단은 참고값이며 실행 시 다시 확인한다.
5. 같은 질문으로 현재 검색을 실행하고, 질문별 검색 원문·시각·점수·응답 시간·오류와 집계 결과를 파일에 남긴다.
6. 실패 사례를 보고 한 가지 조건을 수정해 비교한다. 변경 내용과 이유를 기록한다.

질문 검토가 끝나기 전에는 모델 호출·점수 측정을 하지 않는다. 질문 파일은 `19-search-questions.md`.

## 현재 코드에서 확인한 사실

- 임베딩: KURE-v1. 이 평가로 선정한 모델은 아니다.
- `web/src/lib/search.ts`의 `find`는 현재 임계치로 결과를 거르지 않는다. 답 없는 질문도 결과가 나올 수 있다. 이는 측정 전 코드 확인이며 아직 거절률을 측정한 것은 아니다.
- `web/scripts/eval-search.mjs`에는 AI가 만든 임시 질문 11개가 있다. 정답 구간이 없고 사람 검토가 끝난 평가셋이 아니므로 이번 평가셋으로 그대로 사용하지 않는다.
- 수업 참고: 스프린트 2의 상위 3개 구간 겹침, 스프린트 3의 답 있음/없음 동시 평가. 수업 질문·정답을 Digestube로 복사하지 않는다.

## 실행 기록 양식

| 실행 ID | 질문 버전 | 데이터 스냅샷 | 코드/모델/임계치 | 정답 적중 n/N | 올바른 거절 n/N | 답 있는데 빈 결과 n/N | 오류 수 | 변경·판단 | 원본 결과 파일 |
|---|---|---|---|---|---|---|---|---|---|

아직 실행 기록 없음. 오류를 성공이나 올바른 거절로 세지 않는다. 답 있음·없음 점수는 합산하지 않고 각각 분모와 함께 기록한다.

## 튜닝과 최종 확인

같은 질문을 보며 고친 점수는 개발용 점수다. 임계치나 모델을 고른 뒤에는 튜닝에 사용하지 않은 별도 질문으로 확인한다. 개발용/최종 확인용 질문은 실행 전에 구분하며, 소규모 결과를 전체 서비스 성능으로 일반화하지 않는다.

## 평가 실행 도구 준비

2026-09-11: `web/scripts/run-search-evaluation.ts`와 오프라인 채점 모듈을 추가했다. 실제 검색 호출 없이 25문항 형식 점검과 자동 채점 테스트 4개를 통과했다.

- 기본 실행은 오프라인 점검만 한다. 검색하려면 `--run`을 명시해야 한다.
- 사용자 검수 후 별도 확정본에 `status: frozen`, 각 문항에 `review_status: approved`를 기록한다. 실제 확인 없이 이 값을 변경하지 않는다.
- 현재 10문항은 모두 첫 기준선 측정용이다. 실제 개선안을 정한 뒤에는 이 질문에 맞춰 과도하게 튜닝하지 않고, 별도의 최종 확인 질문을 추가한다.
- 실행 전후 전체 영상 목록, revision, 본문·문단 시각·벡터 해시를 확인한다. 응답 본문과 시각도 해당 스냅샷에 대조한다.
- 질문별 응답 원문, HTTP 상태, 검색 본문·점수·시각, 응답 시간, 오류, 자동 판정을 저장한다. 시간 겹침과 별개로 의미 적합성 검토는 pending으로 남긴다.
- 오류는 성공/올바른 거절로 세지 않으며 각 유형의 전체 문항 수를 분모로 유지한다.
- 배포 ID·모델·임계치 설정은 실행자가 명시한 값이며 서버에서 자동 증명하는 기능은 아니다. 실행 전 실제 배포 설정을 대조해야 한다.
- 합격 판정을 자동으로 내리지 않는다. 응답 시간은 하이라이트 처리를 포함한 전체 요청 시간이며 콜드/웜 구분을 주장하지 않는다.

`web` 폴더에서:

```sh
# 검수 전에도 가능. 외부 요청 없음.
node --import tsx scripts/run-search-evaluation.ts data/evals/search/questions.draft.json

# 실제 검수·버전 고정 후에만 실행한다.
# EVAL_BASE는 평가할 배포 주소, EVAL_DEPLOYMENT는 배포 ID/커밋을 지정한다.
# EVAL_MODEL, EVAL_THRESHOLD는 해당 배포 설정에 맞춘다(현재 기본값 KURE-v1 / none).
node --experimental-websocket --env-file=.env.local --import tsx scripts/run-search-evaluation.ts <확정본.json> --run
```

결과는 `web/data/evals/search/runs/<실행시각>-dev/results.json`과 `summary.md`에 누적한다. 확정본·실행 스냅샷·도구 커밋·변경 여부도 함께 보관한다.

## 검수 전 준비 완료 — 2026-09-11

- `search-review.html`: 질문별 예상 답·원문·재생 링크를 한 화면에서 확인한다. 괜찮음/수정 필요/나중에 보기와 메모를 저장한다. 브라우저 임시 저장과 JSON 다운로드 지원. 부분 검수 파일은 미확정 상태로 남으며 10개를 각각 확인한 경우에만 확정본을 내보낸다. 버튼은 실제 검색을 호출하지 않는다.
- `web/scripts/build-search-review.mjs`: 질문 JSON에서 검수 화면을 재생성한다. 질문 파일이 바뀌면 이전 브라우저 검수 상태를 새 질문에 자동 적용하지 않는다.
- 가짜 API·가짜 DB로 평가 전체 흐름을 테스트했다. 실제 전사문·질문이나 임베딩 서비스를 호출하지 않는다. 원문 응답과 오류 저장, 최종 확인용 분리, 미검수 실행 차단, 실행 중 벡터 변경 감지를 검증한다.
- 실행 보고서 Markdown의 줄바꿈을 수정하고, 길이가 0인 잘못된 검색 구간을 거부한다.
- `web/scripts/compare-search-evaluations.ts`: 동일 질문·기준·검색 범위·본문·문단 경계에서 실행한 두 결과를 비교한다. 모델 비교를 위해 벡터 해시 자체의 차이는 허용하되 각 실행 내부 데이터는 안정적이어야 한다. 실제 모델·설정의 차이는 원본 보고서의 선언값과 배포 기록으로 확인한다. 청킹이 달라진 결과는 상위 3개만으로 공평하게 비교할 수 없어 이 도구에서는 거부한다.

```sh
# web 폴더에서 검수 화면 재생성 (외부 요청 없음)
node scripts/build-search-review.mjs
# 실행이 완료된 뒤 수정 전후 비교 (외부 요청 없음)
node --import tsx scripts/compare-search-evaluations.ts <이전/results.json> <이후/results.json>
```

남은 사용자 작업: 검수 화면에서 질문과 근거를 확인하고 파일을 저장한다. 수정 요청이 있으면 반영 후 다시 확인한다. 그 후 첫 기준선 측정 → 실패 원인 분류 → 한 조건씩 개선 → 새 질문으로 최종 확인 순서로 이어간다. 현재 실제 검색 점수나 모델 우열은 측정하지 않았다.

검증 결과: 단위·DB·가짜 API 통합 테스트 총 21개 통과, 검수 화면 브라우저 테스트 2개 통과, TypeScript·변경 파일 ESLint 통과. 테스트의 가짜 승인 상태는 격리된 테스트 브라우저와 임시 파일에서만 사용하고 실제 질문 파일에는 반영하지 않았다.
